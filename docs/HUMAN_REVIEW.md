## 为什么必须人工，不能由程序自证

程序能算的是「名字像不像」，算不出「是不是同一个东西」。
本项目最重要的两条铁律（**份量/口味不同即不同物**、**组合品不得映射到单品营养**）恰恰是**语义判断**——
只能由人拍板。**用机器给自己判卷，等于把"谁是同一物"这个前提自己定了，然后宣称自己判得准。**

## 流程

```bash
npm run review:samples                      # 1) 生成分层抽样表（≥30 条）
# 2) 人工逐条填「判定」列：same / diff / unknown
npm run review:score -- <csv 路径>           # 3) 汇总精度与误配清单
```

## 判定口径

| 判定 | 含义 | 计入 |
|---|---|---|
| `same` | 机器给的营养来源与菜单项**确为同一物**（份量、口味、规格都一致） | 分子 |
| `diff` | **不是同一物**（四件套配成单品、口味不同、份量不同…） | 分母，并进误配清单 |
| `unknown` | 官方信息不足，无法判断 | **单列**，既不算对也不算错 |
| 留空 | 未审 | **不算通过**（脚本会明确提示「未填不算通过」） |

## 审核完成后要产出

4. 把结果回填到本文件与 `docs/MATCHING_NOTES.md`。

## 误配清单与处置（3 条，同一病根）

三条**全部**是「套餐主件未收录 ⇒ 已知组件之和严重偏低」：

| # | 套餐 | 机器给出的合计 | 实情（AI 预填判定，**待主君确认**） |
|---|---|---|---|
| 13 | 龙焰芝士棒鸡腿堡三件套 | 436 kcal | 仅＝中薯条 289 + 可乐 147；**汉堡本体未收录** |
| 16 | 枫糖风味厚松饼猪柳蛋堡三件套 | 161 kcal | 仅＝脆薯饼 146 + 小杯鲜萃咖啡 15；**主件未收录** |
| 19 | 龙焰鸡腿堡四件套 | 606 kcal | 仅＝中薯条 + 麦乐鸡4块 + 可乐；**汉堡本体未收录** |

**取证**：全快照扫描，**20 个套餐中 7 个**存在主件未收录（均为「龙焰」「枫糖松饼」两个新品系列）。

**处置（v3.2 已落地）**：`src/analyze.ts` 新增主件识别——当未匹配的组件属于**主件**（汉堡/主食/主餐/堡/卷/饭/面/披萨 等）
且非食品周边时，该套餐**不提供营养数字**（关键字段置 null）并**降为 D 级**，notes 写明「主件未收录」。
理由：漏主件时 `≥` 标记不足以抵消误导（436 vs 含汉堡的真实值），与铁律「信息不足时坦率少给」一致。
**非食品组件（帽子等）不计入此判定**，故「"泷"运当头四件套」不受影响。

**回归测试**：`tests/human-review-2026-10-12.test.ts`（5 条）——三条误配现已 D 级无数字；主件齐全者不受影响；
仅漏非食品者不误伤；全快照不变量（凡"主件未收录"必无数字）；主件识别规则本身。
