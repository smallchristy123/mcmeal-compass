# 营养匹配实测笔记（T1.4）

> 采集时间：2026-10-10
> 采集方式：门店 `3450024`（麦当劳重庆嘉年华餐厅），真实 MCP 调用
> 原始留档：`docs/probe/`
> 复现命令：`npm run measure`（离线，读留档）｜ `npm run check:combo`（在线，需 Token）

---

## 一、核心问题

菜单（`query-meals`）与营养表（`list-nutrition-foods`）是**两套独立的命名体系**，
官方**没有提供任何交叉键**。必须自己建立对应关系。

一旦对错，后果是实打实的：把「麦辣鸡腿汉堡三件套」配成「麦辣鸡腿汉堡」的营养，
热量会差出一份中薯条 + 一杯可乐。

---

## 二、实测数据（截至 2026-10-10）

| 指标 | 数值 |
|---|---|
| 营养表条目 | 160 |
| 该门店菜单餐品 | 128 |
| ├ 单品 | 74 |
| └ 套餐/组合 | 54 |
| **整体命中率** | **18.0%（23/128）** |
| ├ 单品命中率 | 31.1%（23/74） |
| └ 套餐命中率 | **0%（0/54）** |
| 营养表条目能对上菜单的比例 | 13.8%（22/160） |

**⚠️ 单看「18%」会误判**：这个数字低，不是匹配算法差，而是**数据的结构使然**——
菜单以套餐为主（54 条），而营养表**只含单品**。套餐名天然不可能出现在营养表里。

---

## 三、关键发现：套餐必须「先展开、再匹配」

实测验证（5 个套餐、20 个组件）：

| 路径 | 命中率 |
|---|---|
| 套餐名 → 直接配营养 | **0%**（0/54） |
| 套餐 → `query-meal-detail` 展开 → 逐件配营养 | ✅ **85%（17/20）** |

**样例**（`全明星双人分享餐八件套`，¥49.90，6 个轮次）：

```
选择汉堡:     麦辣鸡腿汉堡   → ✓ 麦辣鸡腿汉堡
选择主食:     板烧鸡腿堡     → ✓ 板烧鸡腿堡
选择小食:     麦乐鸡4块      → ✓ 麦乐鸡4块
选择小食:     麦辣鸡翅2块     → ✓ 麦辣鸡翅-2块
选择小食:     中薯条        → ✓ 中薯条
选择套餐内饮料: 可乐中杯      → ✓ 可乐中杯
```

> **结论**：主线不是「变着法子模糊匹配」，而是 **`query-meal-detail` 展开 → 组件求和**。
> 这也正是 T1.6（套餐展开与替换校验）的立论依据。

## 四、四级优先级（不命中就认栽，绝不猜）

| 优先级 | 方式 | 说明 |
|---|---|---|
| 1 | `code-mapping` | 人工/预置的 menuCode → 营养品名，最可信 |
| 2 | `exact-name` | 归一化后名称完全相同 |
| 3 | `alias` | 人工别名表命中（含「风险」标注） |
| 4 | `unmatched` | **宁可返回「未知」，也不猜** |

**归一化（`normalizeName`）处理的现实差异**：

- 全半角括号：实测 `纯牛奶(盒装)`（菜单）↔ `纯牛奶（盒装）`（营养表）**已自动对上**；
- 空白、各类连接号（`-` `—` `–` `－` `―`）、`·` `・`；
- 商标符号：`™®©` **必须在 NFKC 之前剥离**——NFKC 会先把 `™` 变成字母 `TM`，
  那时再删就来不及了（实测踩过：`麦咖啡™` → `麦咖啡tm`）。

## 五、⚠️ 「故意不匹配」清单（这是设计，不是缺陷）

以下情形**明确不做映射**，一律落为 `unmatched`：

| 情形 | 实例 | 为何不匹配 |
|---|---|---|
| **份量歧义** | 菜单「薯条」 vs 营养表 中薯条/大薯条/小薯条/迷你薯条 | 4 种可能，**不替用户猜份量** |
| **口味/配方不同** | 菜单「蓝莓爆爆珠麦旋风」 vs 营养表 奥利奥/草莓麦旋风 | 不是同一个东西，配了就是编数据 |
| **新品未收录** | 「龙焰鸡腿堡」「龙焰芝士棒棒鸡腿堡」 | 营养表尚无对应条目 |
| **非食品** | 「旋旋水手帽」「葱不求人按摩捶痒痒挠」 | 本就不是食物 |

> 这对应计划书里「份量歧义高」「名称不一致」两条风险。
> **我们的答案不是把匹配率刷上去，而是把不确定如实标出来。**

## 六、别名表的取舍原则

见 `src/aliases.ts`。三条规矩：

1. **只收「确凿同一物」**；有一丝不确定的宁可不收；
2. **含推断成分的标 `risky: true`**（如「麦辣鸡翅」按常规默认 2 块计），
   匹配时**可信度上限压到 B**，并在说明里写明推断依据——**让人看得见我们猜了什么**；
3. **有多重可能的，一律不收**（如「薯条」）。

当前收录 2 条：`麦辣鸡翅 → 麦辣鸡翅-2块`、`麦乐鸡 → 麦乐鸡5块`（皆标 `risky`）。

## 七、可信度分层（A/B/C/D）

| 级别 | 判据 | 展示策略 |
|---|---|---|
| **A** | 关键营养齐全 **且** 能取到套餐组成 | 正常展示完整营养 |
| **B** | 关键营养齐全，但组成靠推断（或经 risky 别名） | 展示，并注明推断 |
| **C** | 关键营养**部分缺失** | **只展示已知部分**，缺的不补 |
| **D** | 未命中，或关键营养全缺 | **不给营养数字** |

**关键字段**（`KEY_NUTRIENTS`）：`energyKcal` / `protein` / `fat` / `carbohydrate`。
缺任一即为 C；全缺为 D。

> **铁律**：缺失一律 `null`，**绝不填 0**。
> `0` 是「可乐蛋白质为 0」这种真值，与「不知道」是两回事。
