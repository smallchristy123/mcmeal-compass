# 营养匹配实测笔记（T1.4）

> 采集时间：2026-10-10
> 采集方式：门店 `3450024`（麦当劳重庆嘉年华餐厅），真实 MCP 调用
> 原始留档：`fixtures/baseline-20261010-3450024/`（不可变快照）
> 复现命令：`npm run measure`（离线，读留档）｜ `npm run check:combo`（在线，需 Token）

---

## 一、核心问题

菜单（`query-meals`）与营养表（`list-nutrition-foods`）是**两套独立的命名体系**，
官方**没有提供任何交叉键**。必须自己建立对应关系。

一旦对错，后果是实打实的：把「麦辣鸡腿汉堡三件套」配成「麦辣鸡腿汉堡」的营养，
热量会差出一份中薯条 + 一杯可乐。

---

## 二、实测数据（截至 2026-10-10 20:30）

| 指标 | 数值 |
|---|---|
| 营养表条目 | 160 |
| 该门店菜单餐品 | **130**（动态数据；同日 17:04 采集为 128，**数小时内即变**） |
| ├ 单品 | 74 |
| └ 套餐/组合 | 56 |
| **整体命中率** | **19.2%（34/130）** |
| ├ 单品命中率 | **45.9%（34/74）** |
| └ 套餐命中率 | **0%（0/56）** |
| 份量歧义（可解，需用户补输入） | 9 |
| 营养表条目能对上菜单的比例 | 13.8%（22/160） |

**⚠️ 单看「19.2%」会误判**：这个数字低，不是匹配算法差，而是**数据的结构使然**——
菜单以套餐为主（56 条），而营养表**只含单品**。套餐名天然不可能出现在营养表里。

**加入份量维度前后对比**（单品口径）：

| | 命中 | 份量歧义 | 未匹配 |
|---|---|---|---|
| 仅四级优先级 | 23 | 0 | 107 |
| 加入 variant / size-ambiguous 后 | **34** | **9** | 96 |

> 单品命中率 31.1% → **45.9%**。提升主要来自**份量歧义被正确识别**——
> 「薯条」「可乐」这类此前一律算「不知道」，现在能明确告诉用户「请选份量」。

## 三、关键发现：套餐必须「先展开、再匹配」

**全量实测（50 个套餐，178 个组件）**：

| 路径 | 命中率 |
|---|---|
| 套餐名 → 直接配营养 | **0%**（0/50） |
| 套餐 → `query-meal-detail` 展开 → 逐件配营养 | ✅ **组件命中 87.6%（156/178）** |
| ├ 展开成功率 | 100%（50/50） |
| ├ 全部组件都命中的套餐 | 60%（30/50） |
| └ 有 1–2 件配不上的套餐 | 40%（20/50） |

**样例**（`全明星双人分享餐八件套`，¥49.90，6 个轮次）：

```
选择汉堡:     麦辣鸡腿汉堡   → ✓ 麦辣鸡腿汉堡
选择主食:     板烧鸡腿堡     → ✓ 板烧鸡腿堡
选择小食:     麦乐鸡4块      → ✓ 麦乐鸡4块
选择小食:     麦辣鸡翅2块     → ✓ 麦辣鸡翅-2块
选择小食:     中薯条        → ✓ 中薯条
选择套餐内饮料: 可乐中杯      → ✓ 可乐中杯
```

> **结论**：主线不是「变着法子模糊匹配」，而是 **`query-meal-detail` 展开 → 组件求和**。
> 这也正是 T1.6（套餐展开与替换校验）的立论依据。
> 菜单 128 条中套餐占 **50 条（39%）**——**它是主路径，不是支线。**

### 未命中的 22 个组件，按类别拆开

| 类别 | 条数 | 实例 |
|---|---|---|
| **新品未收录** | ~10 | 龙焰系列（4）、枫糖风味厚松饼系列（4）、双层脆鸡堡、Hold不住鸡排堡 |
| **新规格未收录** | 1 | 「麦辣鸡翅**4块**」——营养表只有 `-2块` |
| **非食品混入** | 3 | 旋旋水手帽、旋旋星愿贴、随机玩具 1 个 |
| **包装规格差异** | 3 | 「苹果片一袋(60g)」vs 营养表「苹果片」 |
| **蘸酱类** | 1 | 北美招牌牧场酱 |

> 营养表**滞后于菜单**是数据源的固有属性（160 条中仅 13.8% 能在当前菜单找到）。
> 这不是匹配算法的缺陷，而是**必须诚实告知用户的限制**——这正是「可信度分层」存在的意义。

## 四、匹配规则（不命中就认栽，绝不猜）

| 优先级 | 方式 | 说明 |
|---|---|---|
| 1 | `code-mapping` | 人工/预置的 menuCode → 营养品名，最可信 |
| 2 | `variant` | **用户显式指定份量**（计划书 §5.3.3 的 `variant`） |
| 3 | `exact-name` | 归一化后名称完全相同 |
| 4 | `alias` | 人工别名表命中（含 `risky` 标注） |
| 5 | `size-ambiguous` | **份量歧义**：同名有多个份量 → 列出候选，请用户明确 |
| 6 | `unmatched` | **宁可返回「未知」，也不猜** |

### 关于 `size-ambiguous`（本次新增，计划书 §5.3.3 的 `variant` 维度）

实测菜单里有 9 项属于此类：

```
薯条       → 迷你 / 小 / 中 / 大
可乐       → 小杯 / 中杯 / 大杯
雪碧       → 小杯 / 中杯 / 大杯
卡布奇诺    → 中杯 / 大杯
玉米杯      → 小杯 / 大杯
怡泉+C     → 小杯 / 中杯 / 大杯
鲜萃咖啡     → 中杯 / 大杯
阳光柠檬红茶  → 小杯 / 中杯 / 大杯
```

**这不是「不知道」，而是「等你补一个输入」。** 上游若传入 `variant`（如 `{name:'薯条', variant:'大'}`），
即可直接命中「大薯条」——这比简单判为「无法验证」有用地多。

份量写法有三种（皆实测所见），已全部支持：
前置量词（中薯条）、前置量词+单位（大杯玉米杯）、后置量词（可乐中杯 / 麦辣鸡翅-2块）。

**归一化（`normalizeName`）处理的现实差异**：

- 全半角括号：实测 `纯牛奶(盒装)`（菜单）↔ `纯牛奶（盒装）`（营养表）**已自动对上**；
- 空白、各类连接号（`-` `—` `–` `－` `―`）、`·` `・`；
- 商标符号：`™®©` **必须在 NFKC 之前剥离**——NFKC 会先把 `™` 变成字母 `TM`，
  那时再删就来不及了（实测踩过：`麦咖啡™` → `麦咖啡tm`）。

## 五、⚠️ 「故意不匹配」清单（这是设计，不是缺陷）

以下情形**明确不做映射**，一律落为 `unmatched`：

| 情形 | 实例 | 为何不匹配 |
|---|---|---|
| **份量歧义** | 菜单「薯条」 vs 营养表 中薯条/大薯条/小薯条/迷你薯条 | 4 种可能，**不替用户猜份量** |
| **口味/配方不同** | 菜单「蓝莓爆爆珠麦旋风」 vs 营养表 奥利奥/草莓麦旋风 | 不是同一个东西，配了就是编数据 |
| **新品未收录** | 「龙焰鸡腿堡」「枫糖风味厚松饼猪柳堡」 | 营养表尚无对应条目 |
| **非食品** | 「旋旋水手帽」「随机玩具1个」 | 本就不是食物 |

> 这对应计划书里「份量歧义高」「名称不一致」两条风险。
> **我们的答案不是把匹配率刷上去，而是把不确定如实标出来。**

## 六、命名差异的三条规律（别名表该按规律批量补，而非零散打补丁）

未命中的 22 个组件里，除了「新品未收录」这类无解的，其余差异**有规律可循**：

| 规律 | 实例 | 对策 |
|---|---|---|
| **① 份量后缀** | `麦辣鸡翅` vs `麦辣鸡翅-2块`｜`纯牛奶` vs `纯牛奶(盒装)`｜`苹果片` vs `苹果片一袋(60g)` | 别名表；标 `risky`（份量系推断） |
| **② 套餐组件用简称** | 组件名常省去品牌词/规格词 | 同 ① |
| **③ 非食品混入** | 玩具、贴纸、周边（`旋旋水手帽` 等） | **一律不匹配**，直接判为「非食品」 |

### 别名表的取舍原则

见 `src/aliases.ts`。三条规矩：

1. **只收「确凿同一物」**；有一丝不确定的宁可不收；
2. **含推断成分的标 `risky: true`**（如「麦辣鸡翅」按常规默认 2 块计），
   匹配时**可信度上限压到 B**，并在说明里写明推断依据——**让人看得见我们猜了什么**；
3. **有多重可能的，一律不收**（如「薯条」——已改由 `size-ambiguous` 机制处理）。

当前收录 **5 条**，全部标 `risky`：
`麦辣鸡翅 → 麦辣鸡翅-2块`、`麦乐鸡 → 麦乐鸡5块`、`那么大鸡排（椒盐风味） → 那么大鸡排`、
`100% 苹果汁(盒装) → 100%苹果汁`、`苹果片一袋(60g) → 苹果片`。

### ⚠️ 为什么别名表**不能自动生成**（实测证据）

`scripts/propose-aliases.ts` 用「最长公共前缀」找相似配对，结果**自动产出了 19 组危险诱饵**：

```
✗【95%】菜单「巨无霸四件套」  ←→ 营养表「巨无霸」
✗【95%】菜单「麦香鱼套餐」    ←→ 营养表「麦香鱼」
✗【95%】菜单「双层吉士汉堡套餐」←→ 营养表「双层吉士汉堡」
```

**「四件套」与「单品」相似度高达 95%，但热量差出数倍**（一个四件套 ≈ 单品 + 薯条 + 饮料）。
这正是计划书 §2.3 要防的「胡乱匹配」。故工具只能**提案**，且内置护栏把这类明确标为「必须拒绝」。

> **规则**：组合品（三件套/四件套/套餐/开心乐园餐…）**永远不能映射到单品营养**，
> 必须经 `query-meal-detail` 展开后求和。

### ⚠️ 尚未处理的新发现：**口味歧义**

提案工具还暴露出另一类，与份量歧义同构但本次未处理：

```
「新地」→ 营养表有 朱古力 / 草莓 两种口味
「派」  → 营养表有 香芋 / 菠萝 两种口味
```

**处理方式应同理**：不猜，列出候选请用户明确。已记入待办，本次不改（避免在无充分实测前扩大范围）。

---

### 口味歧义（2026-10-11 补，与份量同类）

实测营养表里同一物的不同口味**是分别列出的独立条目**，故与份量同理处理：**列候选请用户选**。

| 菜单名 | 营养表里的候选 | 说明 |
|---|---|---|
| `新地` | 朱古力新地 / 草莓新地 | 热量与配方不同，不能互相顶替 |
| `派` | 香芋派 / 菠萝派 | 同上 |
| `经典麦旋风` | 奥利奥麦旋风 / 草莓麦旋风 | 「经典」视为修饰词归族 |

判定规则：去掉份量词与口味词后得到**核心名**，同核心且 ≥2 种不同口味即判歧义（`method = flavor-ambiguous`）。
实测全量命中 **恰好 3 项、无假阳性**：`蓝莓爆爆珠麦旋风`（营养表未收录该口味）**仍为未匹配**，绝不拿奥利奥/草莓顶替。

用户可用 `--variant 新地=朱古力` 显式指定；指定后走 `variant` 优先级，并**贯通报价缓存键与解释证据**。

## 七、可信度分层（A/B/C/D）

| 级别 | 判据 | 展示策略 |
|---|---|---|
| **A** | 关键营养齐全 **且** 能取到套餐组成 | 正常展示完整营养 |
| **B** | 关键营养齐全，但组成靠推断（或经 risky 别名） | 展示，并注明推断 |
| **C** | 关键营养**部分缺失** | **只展示已知部分**，缺的不补 |
| **D** | 未命中，或关键营养全缺 | **不给营养数字** |

**关键字段**（`KEY_NUTRIENTS`）：`energyKcal` / `protein` / `fat` / `carbohydrate`。
缺任一即为 C；全缺为 D。

> **铁律**：缺失一律 `null`，**绝不填 0**。
> `0` 是「可乐蛋白质为 0」这种真值，与「不知道」是两回事。
