## 三、评分口径（§6.3 的落实）

| 分量 | 公式 | 何时可用 |
|---|---|---|
| `budgetScore` | `1 - normalize(P)` | 有价格时 |
| `proteinScore` | `normalize(G)` | **仅在用户选「蛋白质优先」或均衡模式下**，且蛋白质非空 |
| `energyFit` | `1 - min(1, \|E - target\| / 容差)` | **仅在用户明确给出本餐热量目标时** |

- **归一化在本轮候选集内进行**（min–max），避免「元 / 克 / kcal」量纲互相压制；
- 上下界相同时给 **0.5**（表示「本批无从区分」），而非最好或最差；
- **容差**默认取目标值的 30%（下限 150 kcal）——这是「吻合度」这一软指标，不是健康判定。

**权重表**（计划书 §6.3 示例值，可调）：

| 模式 | 预算 | 蛋白质 | 热量吻合 |
|---|---:|---:|---:|
| 预算优先 | 0.65 | 0.25 | 0.10 |
| 蛋白质优先 | 0.20 | 0.65 | 0.15 |
| 均衡优先 | 0.35 | 0.35 | 0.30 |

> ⚠️ 这三行是**产品内部启发式，不是医学标准**；实施时无目标项已重归一化。

## 四、三方案的真实差异（§6.4）

不是「同一份结果换三个标题」，而是**三种不同目标各自选出的最优**，并按商品编码去重：

| 方案 | 选择口径 |
|---|---|
| **预算优先** | 预算内实付最低（并列时取蛋白质更高者） |
| **蛋白质优先** | 蛋白质最高（并列时取「蛋白/价格比」更高者） |
| **均衡优先** | 按均衡权重综合分最高（同分时优先落在帕累托前沿上者） |

**实测样例**（门店 3450024，预算 ¥35，离线夹具）：

| 方案 | 选中 | 实付 | 热量 | 蛋白 |
|---|---|---|---|---|
| 预算优先 | 圆筒冰淇淋 | ¥5.00 | 93 kcal | 2 g |
| 蛋白质优先 | 鱼牛汉堡四件套随心选 | ¥32.00 | 1119 kcal | **41 g** |
| 均衡优先 | 那么大鸡排（椒盐风味） | ¥14.50 | 385 kcal | 24 g |

三者价格、营养、取舍各不相同——**用户能真正看到差异**。

## 五、预算全超时的处理（§6.2 第 3 条）

实测中有一处**容易做错的细节**，已修正：

> 若候选在**硬约束阶段**就因「菜单价 > 预算」被剔除，就走不到计价环节——
> 于是给不出「最接近预算的备选」。

**正确做法**：菜单价只用于**预筛**（实付可能因优惠更低），
故这些候选进 `overBudgetPrefilter` **留一手**；若主池最终为空，
再对它们走官方计价，挑出「**最接近且明确超出**」者，并说明「**需你明确同意后才纳入考虑**」。

## 六、解释生成（§6.5）

- 所有差值句（如「蛋白质多 20.0g」「实付多 10.00元」）**由 `diffStatement` 计算**；
- 任一侧缺数据 → 输出「**无法比较**（不做估算）」，**绝不编数字**；
- 每条解释携带 `evidenceIds`（如 `menu:9900005456`、`nut:巨无霸`、`price:…`）与
  **脱敏的 `toolCallTrace`**（门店编码以 `<已脱敏>` 代过，**不含 Token**）。

## 七、当前范围边界（如实记录）

**候选池 = 菜单上的现存商品**（含官方套餐的整体，及其默认组成）。
**尚未实现**的是「从零自由搭配一份餐」（如自选汉堡 + 小食 + 饮料拼成新组合）——
那是 §3.1「一餐 60 秒决策」的完整形态，需在 T2.4 之后扩展。

> 现有能力已可支撑：**按预算与偏好在真实在售商品中选**，并对**套餐内替换**做营养与价格双重重算
> （见 `decompose.ts` 的 `checkSubstitutions`）。

## 附：2026-10-11 外部评审后的口径增补

### 计价（P0-3）
- **每次报价都产出一条结构化收据** `PriceReceipt`：工具名、参数摘要（仅商品码与数量，无 Token/账号）、
  发起时刻、成败、失败分类（如 RATE_LIMITED / TIMEOUT）、重试次数、响应哈希、耗时。
- **解释层的工具轨迹引用真实收据**——不再静态拼装，更不会把失败的调用记成 `ok: true`。
- **有界并发（默认 3）+ 请求预算（默认 200）+ 429 止损**：限流即停，未发起的候选如实标「未发起」。
- **缓存键含门店 / 就餐方式 / 商品 / 数量 / 时间窗**；失败亦如实缓存。
- **合法 0 元报价照用**（0 元 ≠ 没拿到报价）；只有 `price === null` 才回退菜单价并标「未核实实付」。
- `requoteFinal()` 对最终入选方案按实际清单二次报价，并标注是否与初次一致。

### 数据守卫
- **kJ/kcal 换算一致性**（1 kcal = 4.184 kJ）：容差取「相对 5% 或绝对 1 kcal」——
  依据是对 160 条真实数据的实测（偏差中位数 0.13%，极端值仅出现在极小值取整）。
  不一致即判**数据异常**，可信度降到 C 且不得进入完整营养推荐。
- **新鲜度 TTL**：菜单 60 分钟 / 营养与套餐结构 60–1440 分钟 / **价格 10 分钟**（与下单闸门报价时效一致）。
  过期数据**只能作历史样例**，展示层必须写「不代表当前可售，也不是实时价格」。

### 份量与口味的端到端
- `variant` 已贯通「用户输入 → 匹配 → 营养 → 证据」：`--variant 薯条=中` → B 级、289 kcal、来源「官方单品营养：中薯条」。
- 口味歧义（新地/派/经典麦旋风）与份量同法处理：**列候选，不猜**。

### 明确不做（本版本）
- **真实下单**：`create-order` 未接入，`REAL_ORDERING_ENABLED = false`，调用即抛 `ORDERING_DISABLED`，
  且**不发出任何网络请求**。开启前须补齐幂等键、状态机、报价二次校验与重复提交防护。

## v3 更新（2026-10-12 · 外部复评的整改）

外部复评指出「235 项测试全绿并没有覆盖这些用户结果」。以下六处口径**已改**，
逐条对账见 `docs/REVIEW-RESPONSE-v3-2026-10-12.md`：

1. **非价格硬条件统一先验**（`constraints.ts`）
   —— 数据达标 → 最低蛋白 → 避糖 → 正餐范围，**都在菜单价预筛之前**；
   主池、回补池、最终卡片**共用** `checkNonPriceConstraints()`。
   「折扣回补」因此不能再把低蛋白/含糖方案救回来（此前回补只计价、不复验）。
2. **避糖按实际组件判定**（`assessSugary`）
   —— 依据**结构化组件**（`AnalyzedItem.components`）而非展示文案；三态判定
   「明确含糖 / 明确无糖 / 成分未知」，成分未知的疑似饮品**不宣称满足避糖**，零糖商品不再被误杀。
3. **最终复核真正接线**（`recommend.ts::finalizeWithRequote`）
   —— `requoteFinal()` 此前只定义与测试、主流程 0 处调用；现在对每个入选方案按**完整清单**
   （组件 + 数量 + 组成指纹 + 阶段）再报一次价。变价后**重算预算/评分/解释**；
   复核后超预算的方案**撤下**，不拿旧价充数。
4. **价格口径唯一**（`score.ts` 的 `PriceResolver`）
   —— 预算判定、归一化、帕累托、性价比与解释句统一使用**本轮实际采用的价**；
   菜单价只作原始证据。默认取值器仍是菜单价，供未计价场景复用（向后兼容）。
5. **报价对象核对**（`pricing.ts::verifyQuoteBasket`）
   —— 请求与响应的商品/数量必须对得上，否则该报价**标为未核实**；
   合法 0 元（赠品/全额优惠）在对象核对通过时**照常采纳**。
6. **回执只统计真实请求**（`PriceReceipt.channel` + `summarizeReceipts`）
   —— 离线读取 / 缓存命中 / 未发起分别记账，离线即为 **0 次真实请求**；
   取数轨迹由**取数方**产生（`sourceTrace`），解释层只引用，夹具加载不再被写成成功调用。

另：**`--priority` 现在决定首选**（第 1 张卡），三卡仍是三种视角（评审 R10 的甲案）；
新增 `--scope meal|all` 收窄「正餐候选」（默认排除甜品/冰饮/饮品）。

### v3.1 追加（2026-10-12 · 复审 R11–R13）

- **价格来源三态**：`official` / `official-unverified` / `menu`。最终复核未通过时**不得**保留 `official`；
  「已核」措辞要求**来源与 `verified` 同时成立**（R12，P0）。
- **首选元数据随实际方案重算**：最终复核淘汰方案后，`primaryKey`、`primaryNote`、展示顺序、
  `shortfallNote` 一起重算，第一张卡恒等于 `primaryKey`（R11）。
- **收据来自实际调用点**：`query-meal-detail` 的成功/空详情/抛错都在调用处写收据（含 `stage`、`requestId`、
  实际商品 code）；离线与历史来源的成功展开**也不得**记 `ok:true`（R13）。
- **回执含最终复核**：初始 + 最终收据合并重算，`attemptedFailures / offlineNotInitiated / skippedByBudget`
  三者分开（「未发起」不再冒充「失败」）。

### v3.2 追加（2026-10-12 · 人工审核发现的误配）

- **主件未收录 ⇒ 不给营养数字**（`analyze.ts::isStapleComponent`）：套餐的主件（汉堡/主食/主餐等，
  非食品周边除外）未命中官方营养表时，「已知组件之和」严重偏低、`≥` 标记不足以抵消误导，
  故**关键营养字段置 null 并降为 D 级**，notes 写明原因。
  依据：人工审核（35 条）中 3 条 diff 全为此病根；快照内 7/20 套餐受影响，均为新品主件未收录。
- 单品不受此规则影响；主件齐全的套餐与"仅漏非食品组件"的套餐**均不受影响**。
