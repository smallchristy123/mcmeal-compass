## 一、P2：匹配器 API 的 A/B 口径没有同步（**已修**）

复评实测（同一单品、同一输入）：

```
NutritionMatcher.match('巨无霸')              => B   ← 旧口径
NutritionMatcher.matchAll(...).stats          => B: 1
analyzeSingle('巨无霸')                        => A   ← v3.6 新口径
```

| 要素 | 内容 |
|---|---|
| ① 问题 | v3.6 **只改了 `analyzeSingle()` 的调用**，而 `NutritionMatcher.match()` 内部 **5 处仍走旧式** `assignConfidence(row, hasComposition)`；`matchAll().stats` 汇总的正是 `MatchResult.confidence`，于是**对外口径分裂**。CLI 主流程走分析层，故 312 个测试与离线分布都看不出来。 |
| ② 根因（**我方**） | 甲案落地时我只改了「消费端」，**没改「产出端」**——与上一轮 `callTool` 契约变更漏改调用点，是同一种疏忽。 |
| ③ 修改 | `match()` 的**四个分支全部**传入 `{ hasComposition, method, risky }`：`code-mapping` / `variant`（两份量分支）/ `exact-name` / `alias`；`risky` 交由判据**内部**处理（含推断者**最高只到 B**），**删除外层手工降级**。使 `match()` 与 `analyzeSingle()` 同口径。 |
| ④ 实际入口 | `NutritionMatcher.match()` → `matchAll()` / `summarize()` → 任何直接使用匹配器的脚本或后续模块 |
| ⑤ 通过日志 | 新增 `tests/v361-api-consistency.test.ts` **4 条**：① 同一批单品上 `match()` 与 `analyzeSingle()` **逐项同值**且至少一个取到 A；② `matchAll().stats` 与 `summarize()` 同输入**逐档相等**；③ **职责边界差异已文档化**（套餐在匹配器层不得为 A，在分析层可展开为 B/C；A 级全为单品）；④ **单品子集上两种口径的 A/B 分布完全相等**。`npm run gate` **316 用例全绿** |
| ⑥ 适用范围 | 全部导出接口。单品口径已统一；整体分布的口径差异**属职责分工**，非缺陷（见下） |

### 关于复评建议第 3 条（`summarize()` / `matchAll().stats` 与 `analyzeMenu().summary` 同一分布）

**如实说明**：对**同一批菜单项**，二者**不会**给出完全相同的分布，原因是**职责不同**，而非口径错：

| 接口 | 回答的问题 | 套餐类项目 |
|---|---|---|
| `match()` / `matchAll()` / `summarize()` | 「**名称 ↔ 营养表**」是否直配 | **不展开** ⇒ 恒为 `unmatched`（D） |
| `analyzeMenu().summary` | 含**套餐展开**的整体可信度 | 逐项展开求和 ⇒ 可达 **B/C**（主件未收录则 D） |

故本轮采取复评所允许的**第二条路径**：**在导出边界与文档中把口径写清**——
`match()` / `matchAll()` 的 JSDoc 已明写「**不含套餐展开**，整体分布请用 `analyzeMenu().summary`」，
并由上述测试 ③④ 把「整体可有差异、**单品子集必须相等**」固化为断言。

实测（夹具 121 项）：`matchAll().stats` = A 21 / B 4 / C 0 / D 105；
`analyzeMenu().summary` = A 21 / B 15 / C 2 / D 83。
**A 档完全相同（21 项）**，差异全部来自套餐展开（B +11 / C +2 / D −22）——与职责划分一致。
